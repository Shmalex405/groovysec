# AWS S3 Destination Setup Guide

This guide walks you through configuring Amazon S3 as a SOC/SIEM destination in Whiteout AI, batch-exporting audit events into your own bucket for long-term archival and data lake integration.

## Overview

The AWS S3 destination allows Whiteout AI to:
- Export every Whiteout AI event type to an S3 bucket in your AWS account, on an hourly or daily cadence
- Write gzip-compressed JSON Lines or Parquet objects, one folder per event type and time window
- Authenticate by assuming an IAM role in your account with an External ID, so no AWS access keys are stored
- Feed downstream analytics in Athena, Redshift Spectrum, Glue, or your SIEM's S3 ingestion

## Prerequisites

Before you begin, ensure you have:
- **Whiteout AI Admin** privileges
- An **AWS account** with permissions to create S3 buckets, IAM roles and policies, and (optionally) KMS keys
- **AWS Management Console** or **AWS CLI** access

---

## How it works

1. Whiteout AI queues each event for the destination as it happens, with the destination's [privacy settings](#privacy-settings) already applied. Queued events are stored durably, so a restart doesn't lose them.
2. Once a UTC window closes (the hour, or the day for daily cadence), Whiteout AI assumes your IAM role and writes that window's events to your bucket, one object per event type. Whiteout AI checks for closed windows every minute, so objects normally appear within a few minutes of the window closing.
3. The window is the time Whiteout AI queued the event, not the event's own `timestamp`.

## Third-Party Setup

### Step 1: Create an S3 Bucket

Create a dedicated bucket **in the same AWS account as the IAM role** you'll create in Step 4. Whiteout AI writes with an expected-bucket-owner check set to the role's account, so a bucket in another account is rejected.

1. Open the [Amazon S3 console](https://console.aws.amazon.com/s3) and click **Create bucket**
2. Configure the bucket:

| Field | Recommended Value |
|-------|-------------------|
| **Bucket name** | `your-org-whiteout-ai-events` |
| **AWS Region** | Your preferred region; note it for the **Region** field |
| **Object Ownership** | ACLs disabled (recommended) |
| **Block Public Access** | Block all public access (all four options checked) |
| **Bucket Versioning** | Enable (recommended for audit trails) |
| **Default encryption** | SSE-S3, or SSE-KMS if you'll use a KMS key (Step 2) |

3. Click **Create bucket**

### Step 2: Create a KMS Key (Optional)

Whiteout AI encrypts every object with SSE-S3 (AES-256) by default. To use SSE-KMS with your own key instead:

1. In **AWS KMS**, create a symmetric encryption key in the bucket's region
2. Note the key ARN (`arn:aws:kms:<region>:<account-id>:key/<key-id>`)
3. After creating the role in Step 4, make sure the key policy lets the role use the key (the default key policy delegates to IAM, in which case the permissions policy below is enough)

### Step 3: Get the External ID and Policy Templates from Whiteout AI

Whiteout AI generates a per-organization **External ID** and fills in the IAM policies for you:

1. Log in to Whiteout AI as an administrator
2. Go to **Integrations** > **Security Ops Destinations** and click **Add Destination**
3. Set **Destination Type** to **S3 Batch Export**
4. Enter **Bucket**, **Prefix (optional)** and, if you're using one, **KMS Key ARN (optional)**
5. The dialog shows:
   - **External ID**: read-only, generated by Whiteout AI for your organization
   - **Role trust policy**: the trust relationship for your role, with Whiteout AI's AWS principal and your External ID filled in
   - **Role permissions policy**: the permissions your role needs, for your bucket, prefix and key

Copy both policies. You can close the dialog and come back later; the External ID stays the same for your organization.

The templates have this shape:

**Role trust policy**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::<WHITEOUT_ACCOUNT_ID>:root"
      },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": {
          "sts:ExternalId": "<EXTERNAL_ID>"
        }
      }
    }
  ]
}
```

If the dialog shows `<WHITEOUT_ACCOUNT_ID>` rather than an account number, replace it with the account ID you get from Whiteout AI support.

**Role permissions policy**

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "WhiteoutSocExportWrite",
      "Effect": "Allow",
      "Action": [
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::<BUCKET>/<PREFIX>/*"
    },
    {
      "Sid": "WhiteoutSocExportKms",
      "Effect": "Allow",
      "Action": [
        "kms:GenerateDataKey",
        "kms:Encrypt"
      ],
      "Resource": "<KMS_KEY_ARN>"
    }
  ]
}
```

Without a prefix the resource is `arn:aws:s3:::<BUCKET>/*`, and the `WhiteoutSocExportKms` statement is only included when you enter a KMS key. Whiteout AI needs nothing beyond `s3:PutObject`: it never reads, lists or deletes objects.

### Step 4: Create the IAM Role

1. In the IAM console, go to **Roles** > **Create role**
2. Select **Custom trust policy** and paste the **Role trust policy** from Step 3
3. Click **Next**, skip attaching managed policies, and click **Next** again
4. Name the role, e.g. `WhiteoutAI-S3-Export`, and click **Create role**
5. Open the role, go to **Permissions** > **Add permissions** > **Create inline policy**, switch to **JSON**, paste the **Role permissions policy** from Step 3, and save it as `WhiteoutAI-S3-Export-Write`
6. Copy the role's **ARN** (`arn:aws:iam::<account-id>:role/WhiteoutAI-S3-Export`)

If your bucket has a bucket policy, make sure it doesn't deny `s3:PutObject` from this role (for example, a policy requiring a specific encryption type must match the key you chose).

### Step 5: Configure Lifecycle Rules (Recommended)

Set up lifecycle rules for retention:

1. Open your bucket in the S3 console and go to the **Management** tab
2. Click **Create lifecycle rule** and configure, for example:

| Rule | Action | Timeframe |
|------|--------|-----------|
| **Transition to Glacier** | Transition to S3 Glacier Flexible Retrieval | After 90 days |
| **Transition to Deep Archive** | Transition to S3 Glacier Deep Archive | After 365 days |
| **Expiration** | Permanently delete objects | After 2555 days (7 years) or per compliance policy |

3. Click **Create rule**

## Configure Whiteout AI

1. Go back to **Integrations** > **Security Ops Destinations** > **Add Destination** and choose **S3 Batch Export**
2. Fill in the dialog:

| Field | Description |
|-------|-------------|
| **Destination Type** | **S3 Batch Export** |
| **Display Name** | A name for this destination, e.g. `S3 archive` |
| **Prompt content** | **Full text** (default), **Hash only** or **Redacted**. See [Privacy settings](#privacy-settings). |
| **User identity** | **Include email** (default), **Remove email** or **Tokenize**. See [Privacy settings](#privacy-settings). |
| **Bucket** | Your S3 bucket name (no `s3://` prefix) |
| **Prefix (optional)** | Folder inside the bucket, e.g. `whiteout`. Objects go to `<prefix>/<event type>/YYYY/MM/DD/HH/`. |
| **Region** | The bucket's AWS region, e.g. `us-east-1` |
| **IAM Role ARN** | The role from Step 4. Whiteout AI assumes it to write objects; no access keys are stored. |
| **External ID** | Read-only. Generated by Whiteout AI for your organization; the trust policy must require it. |
| **Format** | **JSON Lines (gzip)** (default) or **Parquet** |
| **Cadence** | **Hourly** (default) or **Daily** |
| **KMS Key ARN (optional)** | Encrypt with SSE-KMS using this key. Leave empty for SSE-S3 (AES-256). |
| **Enabled** | On to start queuing events as soon as the destination is saved |

3. Click **Test Connection**. Whiteout AI assumes the role and writes a small test object (see [Verification](#verification)).
4. Click **Create**

> **S3 destinations created before this release** don't deliver until they have a **Region** and an **IAM Role ARN**. Edit the destination, add both, and run **Test Connection**. Until then each export attempt fails, and after 10 failures the destination is disabled; the events already queued are kept and export once it's fixed and turned back on.

## Object layout

Objects are grouped by event type and UTC window:

| Cadence | Object key |
|---------|------------|
| **Hourly** | `<prefix>/<event_type>/YYYY/MM/DD/HH/whiteout-<event_type>-<YYYYMMDDTHH>-<id>.jsonl.gz` |
| **Daily** | `<prefix>/<event_type>/YYYY/MM/DD/whiteout-<event_type>-<YYYYMMDD>-<id>.jsonl.gz` |

Parquet objects end in `.parquet` instead of `.jsonl.gz`. For example:

```
s3://your-org-whiteout-ai-events/whiteout/prompt_log/2026/09/28/14/whiteout-prompt_log-20260928T14-3f9c0e7b2a4d4c1e9f8a7b6c5d4e3f2a.jsonl.gz
```

- An object holds at most **10,000 events** of one event type and one window. Busier windows produce several objects.
- Objects are encrypted with SSE-S3, or SSE-KMS when you set a KMS key.
- Each object carries metadata: `whiteout-event-type`, `whiteout-event-count`, `whiteout-window-start` and `whiteout-cadence`.

### Formats

- **JSON Lines (gzip)**: one event per line, as a JSON object, gzip-compressed (`Content-Type: application/gzip`). Each line is the same event object a webhook receives.
- **Parquet** (Snappy-compressed) with a fixed set of string columns, because event contents vary by type:

| Column | Contents |
|--------|----------|
| `event_id` | The event's ID |
| `event_type` | The event type |
| `timestamp` | The event's timestamp (ISO 8601) |
| `org_id` | Your organization's ID |
| `user_email` | The user's email, after [privacy settings](#privacy-settings) |
| `payload` | The full event as a JSON string |

Changing **Format** or **Cadence** affects objects written from then on; existing objects are unchanged.

## Events delivered

S3 receives every Whiteout AI SIEM event type, each in its own folder under your prefix:

| `event_type` | When it's sent |
|--------------|----------------|
| `prompt_log` | Each governed prompt: allowed, flagged or blocked |
| `prompt_overridden` | A user overrides a block (the block was already sent as `prompt_log`) |
| `coverage_gap` | Shadow-AI discovery opens a coverage-gap finding |
| `connector_vetting_action` | The [Whiteout AI Connector](./whiteout-ai-connector/overview.md) blocks or omits content |
| `report` | A scheduled report run that lists this destination as a **SOC destination** |
| `prompt_injection_detection` | A [Prompt Injection Defense](./injection-defense/overview.md) detection |

Infrastructure agent state alerts are not sent to S3. The event fields are described in [Webhook → Events delivered](./soc-destinations/webhook.md#events-delivered).

### Delivery guarantees

- **At-least-once.** Queued events are removed only after their object is written. If an export is interrupted after the write, the same events can be written again in a new object on the next pass. De-duplicate on `event_id` (for `report` events, on `report.run_id`).
- **Failures and backoff.** A failed export (for example an access-denied error) is recorded on the destination and retried no sooner than 5 minutes later.
- **Auto-disable.** After 10 consecutive failed exports the destination is disabled and admins get a Notification Center alert. Events already queued stay queued while it's disabled and are exported once you fix the cause and turn it back on. Events that happen while it's disabled aren't queued.

## Privacy settings

Every destination has two privacy settings, under **Privacy** in the destination dialog. They apply to every event of every type when it's queued, so changing them affects events queued from then on:

| Setting | Option (`config` value) | Effect |
|---------|-------------------------|--------|
| **Prompt content** (`prompt_visibility`) | **Full text** (`full`, default) | Prompt and response text are stored as captured |
| | **Hash only** (`hash_only`) | Prompt text, response text and injection excerpts become `sha256:<hash>`. Identical prompts can be matched, but not read. |
| | **Redacted** (`redacted`) | Only masked text is stored. A prompt with policy findings is stored with the policy-matched parts masked and the rest of the prompt unchanged. A prompt with no findings, or one that couldn't be masked, is stored as `[CONTENT_REDACTED]`. Response text is always stored as `[RESPONSE_REDACTED]`, and injection excerpts as `[CONTENT_REDACTED]`. |
| **User identity** (`pii_mode`) | **Include email** (`allow`, default) | `user.email` is stored as is |
| | **Remove email** (`strip`) | `user.email` is removed (`null`) from every event |
| | **Tokenize** (`tokenize`) | `user.email` becomes a stable token, `[USER_<hash>]`, in every event, so one user's events can be correlated without revealing who they are |

Masking is done by the Whiteout AI compliance engine and is best-effort. If no prompt text at all may leave Whiteout AI, choose **Hash only**.

The destination card shows the active settings, for example **Privacy: Full text prompts · include email**.

## Verification

1. **Connection Test**: Click **Test Connection** in the dialog, or **Send Test** on the destination card. Whiteout AI assumes the role and writes a small JSON object to `<prefix>/_whiteout_connection_test/whiteout-connection-test-<UTC timestamp>.json`. The role can't delete it, so it stays in place; it's safe to delete.
2. **Bucket Check**: In the S3 console, confirm the test object exists and shows the expected encryption (SSE-S3 or SSE-KMS).
3. **First Export**: Submit a prompt through a governed AI tool. After the current UTC hour (or day) closes, check for an object under `<prefix>/prompt_log/`.
4. **Content Check**: Download the object and inspect it:
   ```bash
   aws s3 cp s3://your-org-whiteout-ai-events/whiteout/prompt_log/2026/09/28/14/ . --recursive
   gunzip -c whiteout-prompt_log-*.jsonl.gz | head
   ```
5. **Destination card**: **Last Delivery** shows the time of the last successful export and **Last Error** the most recent failure.

## Prompt injection detection events

[Prompt Injection Defense](./injection-defense/overview.md) detections are exported to their own folder, `<prefix>/prompt_injection_detection/YYYY/MM/DD[/HH]/`, one line (or Parquet row) per detection with `event_type` `prompt_injection_detection`. In Parquet, the detection details are in the `payload` column. De-duplicate on `event_id`.

The fields, severity mapping and privacy settings are described in [Webhook → Prompt injection detection events](./soc-destinations/webhook.md#prompt-injection-detection-events).

## Configuring through the API

If you manage destinations through the Whiteout AI API rather than the dialog, use `type` `s3` and these `config` keys:

| Dialog field | `config` key |
|--------------|--------------|
| **Bucket** | `bucket` |
| **Prefix** | `prefix` |
| **Region** | `region` |
| **IAM Role ARN** | `role_arn` |
| **External ID** | `external_id` (set by Whiteout AI; a value you send is ignored) |
| **Format** | `format`: `jsonl` (default) or `parquet` |
| **Cadence** | `cadence`: `hourly` (default) or `daily` |
| **KMS Key ARN** | `kms_key_arn` |
| (API only) | `expected_bucket_owner`: the 12-digit account that must own the bucket. Defaults to the role's account. |
| **Prompt content** | `prompt_visibility`: `full` (default), `hash_only` or `redacted` |
| **User identity** | `pii_mode`: `allow` (default), `strip` or `tokenize` |

The older top-level `privacy_profile_id` field is ignored if sent. The External ID and filled-in policy templates are also available from the destinations API's S3 setup endpoint. Flushing an S3 destination through the API exports everything queued immediately, including the window that's still open.

## Troubleshooting

### Test Connection: "Could not assume …"

- Check the role's trust policy matches the **Role trust policy** from the dialog, including the External ID and Whiteout AI's principal
- Check the **IAM Role ARN** is correct

### Test Connection: "Assumed the role but PutObject … failed"

- `AccessDenied`: check the role's permissions policy covers `arn:aws:s3:::<bucket>/<prefix>/*`, and that no bucket policy or SCP denies the write
- With a KMS key: check the permissions policy includes the key and that the key policy allows the role to use it
- The bucket must be owned by the role's AWS account

### No Objects Appearing

- Objects appear only after a UTC window closes: up to an hour (or a day) after the first event
- Check **Last Error** on the destination card, and whether the destination has been disabled after repeated failures
- Check the destination is **Enabled**: events aren't queued while it's disabled

### Large or Many Objects

- Switch to **Hourly** cadence for smaller objects, or **Daily** for fewer objects
- Busy windows are split into objects of up to 10,000 events

## Security Considerations

- **Block Public Access**: Keep all public access blocked on the bucket. Audit events contain sensitive information.
- **Require the External ID**: Keep the `sts:ExternalId` condition in the trust policy. It stops another Whiteout AI customer from pointing Whiteout AI at your role.
- **Least Privilege**: The role needs only `s3:PutObject` on the prefix (plus KMS use if you set a key). Don't grant read, list or delete.
- **Encryption**: Objects are always encrypted at rest; use SSE-KMS with your own key for key-level control and CloudTrail auditing.
- **Limit Content**: Use **Prompt content** and **User identity** to store only what the bucket is cleared to hold.
- **Enable Access Logging**: Turn on S3 server access logging or CloudTrail data events for the bucket.
- **Retention Lock**: For strict compliance requirements, consider S3 Object Lock in Governance or Compliance mode.
