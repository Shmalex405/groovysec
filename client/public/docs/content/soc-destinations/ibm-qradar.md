# IBM QRadar Destination Setup Guide

This guide walks you through configuring IBM QRadar as a SOC/SIEM destination in Whiteout AI, forwarding audit events as CEF over TLS syslog for SIEM correlation and compliance reporting.

## Overview

The IBM QRadar destination allows Whiteout AI to:
- Forward every Whiteout AI event type to QRadar, one CEF (Common Event Format) event per syslog message
- Encrypt events in transit with TLS syslog (RFC 5425), verifying QRadar's certificate by default
- Use QRadar's rules engine to detect suspicious AI usage and raise offenses
- Correlate Whiteout AI events with your other log sources for threat analysis and compliance reporting

## Prerequisites

Before you begin, ensure you have:
- **Whiteout AI Admin** privileges
- **IBM QRadar** (7.4 or later) or **QRadar on Cloud**
- **QRadar Admin** access to create log sources and deploy changes
- Network connectivity from Whiteout AI to your QRadar Event Collector or Console on the TLS syslog port (default `6514/tcp`)
- A TLS certificate for the listener. If it isn't from a publicly trusted CA, you'll need the issuing CA certificate in PEM format.

## Third-Party Setup

### Step 1: Create a TLS Syslog Log Source

The TLS Syslog log source opens the listener that Whiteout AI connects to.

1. Log in to the QRadar Console
2. Open **Admin** > **Log Sources** (the QRadar Log Source Management app)
3. Click **New Log Source** > **Single Log Source**
4. Select the log source type **Universal CEF**, then the protocol **TLS Syslog**
5. Configure the log source:

| Field | Value |
|-------|-------|
| **Name** | `Whiteout AI` |
| **Description** | Audit events from Whiteout AI |
| **Log Source Identifier** | `whiteout-ai` |
| **Enabled** | Yes |
| **Event Collector** | The collector Whiteout AI will connect to |
| **TLS Listen Port** | `6514` (or another port; you'll enter the same one in Whiteout AI) |
| **Authentication Mode** | **TLS**. Whiteout AI doesn't present a client certificate. |
| **Certificate Type** | Provide your own certificate and key, or let QRadar generate one |

6. Save the log source, then click **Deploy Changes** on the **Admin** tab

Every message Whiteout AI sends has the syslog hostname `whiteout-ai`, which is why the **Log Source Identifier** must be exactly `whiteout-ai`.

### Step 2: Prepare the Certificate

Whiteout AI verifies the listener's certificate by default, including that it matches the **Syslog Host** you enter:

- **Certificate from a publicly trusted CA**: nothing more to do.
- **Certificate from a private CA, or generated by QRadar**: copy the issuing CA certificate (PEM, starting `-----BEGIN CERTIFICATE-----`). You'll paste it into **CA Certificate** in Whiteout AI. For a QRadar-generated self-signed certificate, the certificate itself is the CA.

Make sure the certificate's subject alternative names include the host name or IP address you'll use as **Syslog Host**.

### Step 3: Open the Network Path

1. Allow inbound TCP from Whiteout AI to the Event Collector on the **TLS Listen Port**
2. If you want to check the listener from your own network first:
   ```bash
   openssl s_client -connect qradar-ec.example.com:6514 -servername qradar-ec.example.com
   ```
   A successful handshake shows the certificate chain.

### Step 4: Map Events and Create Rules (Optional)

The Universal CEF DSM parses the CEF header and extension keys. To give events meaningful QRadar names and categories:

1. Open **Admin** > **DSM Editor** and select **Universal CEF**
2. Map the event IDs (the CEF signature IDs in [CEF field mapping](#cef-field-mapping), for example `prompt_log:blocked` or `prompt_injection_detection:block`) to QRadar QIDs
3. Add custom properties for the extension keys you want to search on, for example `suser`, `act`, `cat`, `cs5` (policies) or `cs3` (categories for injection events)

Example rules (**Offenses** > **Rules** > **Actions** > **New Event Rule**):

**Blocked AI prompt**:
- When the event matches `Log Source = Whiteout AI` AND event ID is `prompt_log:blocked`
- Action: create an offense with severity `8`, category Policy Violation

**Repeated blocks by the same user**:
- When `Log Source = Whiteout AI` AND event ID `prompt_log:blocked` occurs more than 5 times in 10 minutes, grouped by username (`suser`)
- Action: create an offense with severity `7`, category Anomalous Activity

## Configure Whiteout AI

1. Log in to Whiteout AI as an administrator
2. Go to **Integrations** > **Security Ops Destinations** and click **Add Destination**
3. Fill in the dialog:

| Field | Description |
|-------|-------------|
| **Destination Type** | **QRadar (TLS Syslog/CEF)** |
| **Display Name** | A name for this destination, e.g. `QRadar` |
| **Privacy Profile** | Leave at **(None)**. See [Privacy settings](#privacy-settings). |
| **Syslog Host** | Hostname or IP of your QRadar Event Collector / Console. Events arrive with hostname `whiteout-ai`; use it as the Log Source Identifier. |
| **Port** | TLS Syslog listener port (default `6514`) |
| **Verify TLS certificate** | On by default. Leave it on in production. |
| **CA Certificate (PEM, optional)** | Only needed if the QRadar listener uses a certificate from a private CA (Step 2) |
| **Enabled** | On to start delivering as soon as the destination is saved |

4. Click **Test Connection**. Whiteout AI connects, performs the TLS handshake and sends one test event (see [Verification](#verification)).
5. Click **Create**

> **Destinations created before this release.** QRadar destinations saved earlier now deliver without being re-entered, but earlier versions used plain syslog on port `514`. Edit the destination, set **Port** to your TLS Syslog listener port (or clear it for `6514`), and run **Test Connection**.

## Wire format

Each event is one RFC 5424 syslog message with a CEF payload, sent over TLS (1.2 or later) with RFC 5425 octet-counted framing (`<length> <message>`):

```
<PRI>1 <timestamp> whiteout-ai WhiteoutAI - <event_type> - CEF:0|Groovy Security|Whiteout AI|<version>|<signature ID>|<name>|<severity>|<extensions>
```

- **PRI** uses facility `local0` and a syslog severity derived from the CEF severity: 9–10 → critical, 7–8 → error, 5–6 → warning, 3–4 → notice, 0–2 → informational
- **Timestamp** is the event time in UTC with milliseconds
- **Hostname** is always `whiteout-ai`, the app name `WhiteoutAI`, and the message ID the event type
- **Version** is the Whiteout AI release that sent the event
- CEF escaping follows the ArcSight CEF specification: `\` and `|` are escaped in the header; `\`, `=` and line breaks are escaped in extension values. Empty fields are omitted.

Example (a blocked prompt):

```
582 <131>1 2026-09-28T14:03:11.123Z whiteout-ai WhiteoutAI - prompt_log - CEF:0|Groovy Security|Whiteout AI|X.Y.Z|prompt_log:blocked|AI prompt blocked|8|rt=1790604191123 externalId=6f1c2a4e-9b8d-4e7f-a1c3-2d5e8f9a0b1c cat=prompt_log suser=dev@example.com cs1Label=orgId cs1=5f0c2d1e-8b7a-4c3d-9e6f-1a2b3c4d5e6f cs2Label=group cs2=Engineering act=blocked outcome=blocked reason=Contains customer PII requestClientApplication=ChatGPT cs3Label=sourceType cs3=browser cs5Label=policies cs5=PII-001 cs6Label=promptText cs6=Summarize the attached customer list cn1Label=riskFindingCount cn1=1
```

## CEF field mapping

### Fields on every event

| CEF key | Contents |
|---------|----------|
| `rt` | Event time (epoch milliseconds) |
| `externalId` | `event_id`. Use it to de-duplicate. |
| `cat` | `event_type` |
| `suser` | `user.email` |
| `suid` | `user.id` |
| `cs1` (`orgId`) | Your organization's ID |
| `cs2` (`group`) | Group name, or group ID when there's no name |

### Signature IDs, names and severities

| `event_type` | Signature ID | Name | CEF severity |
|--------------|--------------|------|--------------|
| `prompt_log` | `prompt_log:blocked` | AI prompt blocked | 8 |
| | `prompt_log:overridden` | AI prompt sent after override | 6 |
| | `prompt_log:flagged` | AI prompt flagged | 5 |
| | `prompt_log:allowed` | AI prompt allowed | 2 |
| `prompt_overridden` | `prompt_overridden` | AI prompt block overridden | 6 |
| `coverage_gap` | `coverage_gap:<finding type>` | Shadow AI coverage gap | From the finding's severity (low 3, medium 5, high 8, critical 10); 5 if unset |
| `connector_vetting_action` | `connector_vetting_action` | AI connector content blocked | 6 when content was blocked, 4 when only omitted |
| `report` | `report:<status>` | Scheduled report `<status>` | 5 for a failed run, 1 otherwise |
| `prompt_injection_detection` | `prompt_injection_detection:<action>` | Prompt injection detected | high 8, medium 5, low 3 |
| Connection test | `connection_test` | Whiteout AI connection test | 1 |
| Any other event type | The event type | The event type in words | From the event's `severity`; 3 if unset |

### Fields per event type

| `event_type` | CEF extensions |
|--------------|----------------|
| `prompt_log`, `prompt_overridden` | `act` (blocked, overridden or allowed), `outcome`, `reason` (policy violation reason), `requestClientApplication` (AI tool), `cs3` (`sourceType`), `cs4` (`model`), `cs5` (`policies`), `cs6` (`promptText`), `flexString1` (`responseText`), `flexString2` (`chatId`), `cn1` (`riskFindingCount`) |
| `coverage_gap` | `act=detected`, `requestClientApplication` (tool catalog key), `cs3` (`sourceType`), `cs4` (`category`), `cs5` (`findingType`), `cs6` (`sourceId`), `cn1` (`daysObserved`), `start` / `end` (first and last seen), `msg` (recommended action), `request` (link to the finding) |
| `connector_vetting_action` | `act` (blocked or omitted), `requestClientApplication` (connector tool), `cs3` (`integration`), `cs4` (`policyCategory`), `cs5` (`policies`), `cs6` (`fieldsBlocked`), `cn1` (`blockedCount`), `cn2` (`existenceClassifiedCount`), `cn3` (`allowedCount`), `flexString1` (`policySet`) |
| `report` | `act` (run status), `msg` (title), `cs3` (`reportName`), `cs4` (`runId`), `cs5` (`containsContent`), `start` / `end` (report window), `request` (download link), `fileHash` (SHA-256), `cn1` (`pages`) |
| `prompt_injection_detection` | `act` (detection action), `requestClientApplication` (surface), `cs3` (`categories`), `cs4` (`ruleIds`), `cs5` (`sourceKind`), `cs6` (`excerpt`), `cfp1` (`score`), `flexString1` (`scanId`), `flexString2` (`tier`), `request` (link to the scan) |
| Any other event type | `msg`: the event as compact JSON, without the common fields |

Each `csN`, `cnN`, `cfpN` and `flexStringN` value is accompanied by its `…Label` key, shown in brackets above.

### Truncation

Long values are cut to fit and end with `...[truncated]`:

| Field | Limit (characters) |
|-------|--------------------|
| Prompt text (`cs6` on prompt events), injection excerpt (`cs6`), generic `msg` | 2,048 |
| Response text (`flexString1` on prompt events) | 1,024 |
| Other text fields | 1,023 |

## Events delivered

QRadar receives every Whiteout AI SIEM event type: `prompt_log`, `prompt_overridden`, `coverage_gap`, `connector_vetting_action`, `report` (when a scheduled report lists this destination as a **SOC destination**) and `prompt_injection_detection`. Infrastructure agent state alerts are not sent to QRadar. The event fields are described in [Webhook → Events delivered](./soc-destinations/webhook.md#events-delivered).

- **Batching**: prompt events are batched (500 events or 5 seconds by default) and each batch is sent over one TLS connection, one message per event. Other events are sent as they occur.
- **Retries**: connection failures and timeouts are retried, up to 3 attempts. TLS errors, such as a certificate that can't be verified, aren't retried because they need a configuration change.
- **Duplicates**: a retry resends the whole batch, so if a connection drops part-way through, QRadar can receive some events twice. De-duplicate on `externalId`.
- **Auto-disable**: after 10 consecutive failed deliveries the destination is disabled and admins get a Notification Center alert. Fix the cause, then turn it back on.

## Privacy settings

Each destination applies two privacy settings to every event before it's converted to CEF:

| Setting | Value | Effect |
|---------|-------|--------|
| `prompt_visibility` | `full` (default) | Prompt and response text are sent as captured (subject to the truncation limits) |
| | `hash_only` | Prompt text, response text and injection excerpts become `sha256:<hash>` |
| | `redacted` | Policy-matched parts of the prompt are masked; the response becomes `[RESPONSE_REDACTED]` when the prompt was blocked; injection excerpts become `[CONTENT_REDACTED]`. Prompts with no findings are sent unchanged. |
| `pii_mode` | `allow` (default) | `suser` carries the user's email |
| | `strip` | The email is removed, so `suser` is omitted, on every event |
| | `tokenize` | `suser` becomes a stable token, `[USER_<hash>]`, on every event |

Set them in the destination's configuration through the API (see [Configuring through the API](#configuring-through-the-api)). The **Privacy Profile** list in the dialog doesn't set them, so leave it at **(None)**.

## Verification

1. **Connection Test**: Click **Test Connection** in the dialog, or **Send Test** on the destination card. On success, Whiteout AI reports the TLS version and whether the certificate was verified, and sends one event with signature ID `connection_test`.
2. **Log Activity**: In QRadar, open **Log Activity**, filter on the `Whiteout AI` log source, and confirm the **Whiteout AI connection test** event arrived.
3. **Event Parsing**: Open the event and check the CEF fields are parsed (for example `cat` and `externalId`).
4. **End-to-End Test**: Submit a prompt through a governed AI tool and confirm a `prompt_log:…` event arrives within a few seconds.
5. **Offense Generation**: If you configured rules, trigger a matching event and check the **Offenses** tab.

## Prompt injection detection events

[Prompt Injection Defense](./injection-defense/overview.md) detections arrive as CEF events with signature ID `prompt_injection_detection:<action>` (for example `prompt_injection_detection:block`), name **Prompt injection detected**, and a CEF severity of 8, 5 or 3 for the event's `high`, `medium` or `low` severity. The attack categories are in `cs3`, the rule IDs in `cs4`, the part the text came from in `cs5`, the excerpt (when your organization keeps excerpts) in `cs6`, the score in `cfp1` and the scan link in `request`.

The fields, severity mapping and privacy settings are described in [Webhook → Prompt injection detection events](./soc-destinations/webhook.md#prompt-injection-detection-events).

## Configuring through the API

If you manage destinations through the Whiteout AI API rather than the dialog, use `type` `qradar` and these `config` keys:

| Dialog field | `config` key |
|--------------|--------------|
| **Syslog Host** | `syslog_host` |
| **Port** | `syslog_port` (default `6514`; the older name `port` is also accepted) |
| **Verify TLS certificate** | `verify_tls` (default `true`) |
| **CA Certificate** | `ca_cert` (PEM) |
| (API only) | `framing`: `octet` (default, RFC 5425 octet counting) or `lf` (newline-terminated messages) |
| (API only) | `prompt_visibility`, `pii_mode` (see [Privacy settings](#privacy-settings)) |

Batching is set with the top-level `batching_max_events` (default `500`) and `batching_max_seconds` (default `5`).

## Troubleshooting

### Test Connection: "Could not connect" or "timed out"

- Check the **Syslog Host** and **Port**, and that the log source has been deployed (the listener only opens after **Deploy Changes**)
- Confirm firewalls allow TCP from Whiteout AI to the Event Collector on the listener port

### Test Connection: "TLS certificate verification failed"

- Paste the issuing CA certificate (PEM) into **CA Certificate**
- Make sure the certificate names the host you entered as **Syslog Host**
- Check the certificate hasn't expired

### Test Connection: "TLS handshake failed"

- Confirm the port is a **TLS Syslog** listener, not plain TCP or UDP syslog
- Check the log source's **Authentication Mode** is **TLS** (not client-certificate authentication) and that it allows TLS 1.2 or later

### Events Not Appearing or Shown as Unknown

- Check the **Log Source Identifier** is exactly `whiteout-ai`
- Check the log source type is **Universal CEF**
- Disable automatic log source detection for this collector if QRadar created a second log source for the same traffic
- Check **Last Error** on the destination card, and whether the destination has been disabled after repeated failures

### Duplicate Events

- Retries resend the whole batch. De-duplicate on `externalId`, or build rules that tolerate repeats.

### Truncated Fields

- Prompt and response text are truncated to the limits in [Truncation](#truncation). Use a webhook, Splunk or S3 destination if you need full text.

## Security Considerations

- **Keep Certificate Verification On**: Turn off **Verify TLS certificate** only for testing. Use **CA Certificate** for private CAs instead.
- **Restrict Network Access**: Allow only Whiteout AI to reach the TLS syslog port.
- **Limit Content**: QRadar receives prompt text by default. Use `prompt_visibility` and `pii_mode` to send only what QRadar is cleared to hold.
- **Monitor Log Source Health**: Set up QRadar system notifications for when the Whiteout AI log source stops receiving events.
- **Protect QRadar Access**: Restrict the QRadar Admin console to authorized security personnel.
- **Retention Policies**: Set retention for Whiteout AI events based on your compliance requirements (e.g., 90 days, 1 year, 7 years).
- **Regular Audits**: Periodically review QRadar rules, offenses, and log source configuration.
